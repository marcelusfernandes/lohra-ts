# Síntese das falhas residuais nativas do Windows (#754)

Esta síntese reconcilia o [inventário #751](failure-triage-inventory.md) com as [sondas de `serve` e compactação #752](failure-triage-runtime.md) e de [permissões, sinais e SQLite #753](failure-triage-platform.md). O inventário mediu `main` em `ebeb722f898bdb4cde5b7d7cef66fb40febf5c15`, Windows 11 x64, Node 20.20.2/npm 10.8.2 e Node 22.23.2/npm 10.9.8, em clones independentes após `npm ci`. As triagens mediram o SHA posterior `4850b36079620f30f0d51621219f0e5fb4e646d2`; seus focais não substituem a suíte do inventário. Esta PR só organiza evidências e não altera produto ou testes.

O [projetor](evidence/failure-triage/summary/project.mjs) lê as projeções JSONL versionadas do inventário e produz uma [linha por ID estável](evidence/failure-triage/summary/assignments.jsonl), com presença por Node, arquivo, família, estado, issue e próximo experimento. `node docs/investigations/windows/evidence/failure-triage/summary/project.mjs --check` compara os artefatos versionados byte a byte e falha se uma contagem ou associação mudar. Os grupos `unresolved:<arquivo>` e `sqlite-unresolved:<arquivo>` **não** afirmam causa comum entre seus membros: mantêm o arquivo e o experimento necessários para separá-los. Cada ID pertence a exatamente uma família; uma asserção presente nos dois Nodes continua sendo um único ID.

Restam **189/190 assertions INCONCLUSIVE**, não convertidas em PASS. Em ambos os Nodes, 57 IDs em 11 outros arquivos trazem `unlink state.db`; a sonda #753 mostra que um handle aberto _pode_ causar esse sintoma, mas não identifica o handle em cada fixture. Outros cinco IDs com expectativa de bits POSIX e quatro de `mutations-all`/sinal têm medições de plataforma em #753 sem prova da causa específica. Há ainda 123 IDs no Node 20 e 124 no Node 22 com outras assinaturas, incluindo `npm pack` com exit nulo, `ERR_MODULE_NOT_FOUND` no stub driver, CRLF e caminhos Windows; sem experimento focal, esses textos não viram causas confirmadas. O único `chat-compaction-events` investigado em #752 passou 5/5 em cada Node no inventário e no focal, logo não cria família residual. `tests/workflow-service-durability.test.ts` passou 34/34 em ambos; a #787 bloqueada não explica automaticamente os demais `EBUSY`.

Hipóteses já têm trabalho delimitado sem promoção antecipada a causa confirmada: [#809](https://github.com/marcelusfernandes/lohra-ts/issues/809) investiga separadamente home/caminho Windows em `state-schema` e CRLF do terminal em `gateway/tools`; [#810](https://github.com/marcelusfernandes/lohra-ts/issues/810) mede o `URL.pathname` do stub driver antes de atribuir seus três `ERR_MODULE_NOT_FOUND`; [#811](https://github.com/marcelusfernandes/lohra-ts/issues/811) mede a fixture `workflow-leaf-read-tool` (13 `EBUSY`); [#812](https://github.com/marcelusfernandes/lohra-ts/issues/812) mede a resolução de `sh` nas quatro bancadas com 63 IDs; [#813](https://github.com/marcelusfernandes/lohra-ts/issues/813) mede as fixtures SQLite de `rpc-dispatch` e `raw-socket-primitives` (8+6 IDs); [#814](https://github.com/marcelusfernandes/lohra-ts/issues/814) mede `prompt-submit` (16 IDs). A [atribuição por ID](evidence/failure-triage/summary/assignments.jsonl) vincula essas issues com estado **INCONCLUSIVE** até a respectiva reprodução. A sonda `sh` do host atual observou `ENOENT` para o nome e sucesso com o caminho Git explícito, mas não reproduziu o ambiente isolado do inventário; não confirma a causa dos 63 IDs.

Também foram abertas [#815](https://github.com/marcelusfernandes/lohra-ts/issues/815) para os dois IDs de `npm pack` em `package-manifest` e [#816](https://github.com/marcelusfernandes/lohra-ts/issues/816) para o ID de `self-update`. Uma sonda limitada do runner de self-update mostrou perda da causa de spawn e `TypeError` em `Buffer.from` no host atual, mas não reproduziu o ID do inventário; ambos permanecem **INCONCLUSIVE**.

As [34 ocorrências secundárias](evidence/failure-triage/summary/secondary.jsonl) são 17 por Node, **dentro** de assertions já contadas: 16 `unlink state.db` e uma `rmdir` em cada. Cada registro aponta para o ID da asserção e sua família primária, mas `causalRelation: NOT_DEMONSTRATED` impede afirmar que o erro primário causou o cleanup ou o inverso. Os [14 registros de stderr](evidence/failure-triage/summary/stderr.jsonl) são sete por Node, seis `ELOOP` de paths/skills e um aviso de shadowing MCP; são `UNATTRIBUTED_DIAGNOSTIC`, sem ID de teste. O reporter não expôs `unhandledErrors`: **NOT_REPORTED**, nunca “zero”. Próximos experimentos: fixture isolada de caminhos/skills para `ELOOP` e registro MCP isolado para shadowing, sem somá-los às assertions.

O aceite [#736](https://github.com/marcelusfernandes/lohra-ts/issues/736) permanece bloqueado pelos IDs inconclusivos, pela leitura ACL efetiva não medida e pelas correções vinculadas ainda pendentes. Provider live, outros ambientes Windows e causalidade entre mensagens primárias/secundárias não foram medidos. As linhas e contagens deste relatório são a projeção do ensaio nativo fixado, não um relatório de suporte Windows concluído.
