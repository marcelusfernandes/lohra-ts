# Encerramento nativo dos servidores no Windows (#730)

**Resultado:** em Windows 11 x64 (build 26200), no código-base `4f709668db1d841555929a1023bb3a4d99ea6314`, Ctrl-C entregue por ConPTY encerrou naturalmente `serve` e `dashboard` sem cliente WebSocket ativo, com código 0 em Node 20.20.2 e 22.23.2. A porta fechou; no `dashboard`, o arquivo `state.db` pôde ser renomeado e o diretório temporário removido. **Falha confirmada:** com `/api/ws` aberto, o `dashboard` permaneceu vivo por 2,5 s após Ctrl-C em ambos os Nodes; saiu com código 0 somente após o cliente fechar o WebSocket. A falha está registrada na subissue [#792](https://github.com/marcelusfernandes/lohra-ts/issues/792), vinculada a #730. Os [comandos](evidence/shutdown-validation/reproduction.md), [fontes das sondas](evidence/shutdown-validation/server-probe.cjs) e JSONs por cenário estão preservados.

## Ambiente e isolamento

- Windows NT 10.0.26200.0, x64; Node oficial portátil 20.20.2 e Node instalado 22.23.2. Dois clones descartáveis separados em `F:` receberam build exit 0, cada qual com dependências nativas da própria ABI. `package-lock.json` SHA-256 `A7E0DE3A40F4B19435114F3FB23AC674802BDC93055ABC921249617659A6CC01`.
- Cada processo servidor recebeu `LOHRA_HOME`, `CODEX_HOME`, `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `TEMP` e `TMP` sob diretório temporário exclusivo. A sonda construiu uma allowlist de ambiente e não transmitiu chaves do host. O perfil Ollama foi selecionado para evitar autenticação real; os requests HTTP de prontidão não invocaram modelo (`stubRequests=0`). O stub configurado para `dashboard` escutou apenas em loopback. `serve` respondeu `/health` e `dashboard` respondeu `/api/status`, ambos com HTTP 200.
- ConPTY entregou `\x03` a uma sessão de console real. Uma [sonda mínima de SIGINT](evidence/shutdown-validation/signal-probe.cjs) gravou `SIGINT_HANDLER` de dentro de um filho Node antes de sair com código 0 nos [Node 20](evidence/shutdown-validation/signal-node20.json) e [22](evidence/shutdown-validation/signal-node22.json). Nas sondas de CLI, `child.kill()` foi chamado **depois** do evento `onExit` para liberar o handle ConPTY; não causou a saída medida. O controle `child_process.spawn` + `child.kill('SIGTERM')` é separado e não foi tratado como shutdown gracioso.
- As fontes das três sondas estão em [signal-probe.cjs](evidence/shutdown-validation/signal-probe.cjs), [server-probe.cjs](evidence/shutdown-validation/server-probe.cjs) e [ws-shutdown-probe.cjs](evidence/shutdown-validation/ws-shutdown-probe.cjs). Seus prazos limitam espera e encerram apenas processos filhos próprios; os logs JSON retêm PIDs efêmeros da sonda, nenhum segredo ou saída bruta de CLI.

## Causa e limite da conclusão

O bloqueio com WS ativo é consistente com a ordem implementada: `dashboard.ts:605-615` aguarda `server.close()` para só então chamar `closeResources("signal")`; `gateway/http/server.ts:133-138` resolve `close()` apenas no callback de `net.Server.close`. No upgrade, `gateway/http/server.ts:17-21,66-70` transfere o socket ao handler WS, e `gateway/ws/connection.ts:404-415` cria `WebSocketServer` sem expor fechamento das conexões ao shutdown. A sonda fecha o cliente e o processo então termina, repetido em duas ABIs. Isto demonstra uma conexão que mantém o encerramento pendente; não mede o comportamento de todos os estados de WS, nem tempo de flush de cada subsistema. A implementação de #792 deve testar saída natural com WS mantido aberto e fechamento bounded de clientes, preservando ordem e causa.

Para o caso ocioso, código 0, porta fechada e arquivo renomeável demonstram que o caminho de shutdown e liberação do handle SQLite terminou. Renomear arquivo também é possível depois de morte forçada, como mostra o controle SIGTERM; portanto esse controle não prova execução do handler. Nenhuma sonda inspecionou todas as escritas do banco ou a resposta de um provider real. Não se declara suporte Windows global a partir desses cenários.

## Verificação documental

Esta issue não altera produção/testes. `npm run prova -- windows-server-shutdown` não existe como prova declarada: o Proof da issue é N/A, substituído por fontes e JSONs. Quatro gates nativos Node 22 e cinco gates Linux do SHA deste relatório serão registrados na PR; seus resultados não reclassificam a falha WS. O aceite da correção exige #792 e teste regressivo antes/depois.
