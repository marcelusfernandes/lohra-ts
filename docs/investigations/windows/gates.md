# W2 — gates nativos no Windows (#702)

Medição em 2026-10-02 do commit `fa8aa4a572a8d84c3eea128a7ce67ab4eac796e1`, em Windows 11 x64 (`OSDescription: Microsoft Windows 10.0.26200`), PowerShell 7.6.5. O clone padrão da investigação #701 falhou no caminho `aux.ts`; esta medição usa dois clones descartáveis obtidos com `git -c core.protectNTFS=false clone`, com `npm ci` concluído separadamente para Node 20.20.2/npm 10.8.2 e Node 22.23.3/npm 10.9.9. Para preservar a medição de instalação, cada clone foi copiado para uma área temporária própria antes dos gates. `HOME`, `USERPROFILE`, `TEMP`, `TMP`, caches/prefixo npm, `LOHRA_HOME` e `CODEX_HOME` apontaram para diretórios temporários exclusivos por versão. Não houve provedor real nem uso do home Lohra do usuário.

Os comandos foram executados com `node.exe <distribuição-portátil>/node_modules/npm/bin/npm-cli.js ...` e `PATH` começando pelo Node correspondente. Essa é a invocação explícita de `npm run ...`/`npm test` sob o Node medido; o comando e o código de saída exatos, duração, limite, horário UTC e hashes SHA-256 dos logs estão em [node20.json](evidence/gates/node20.json) e [node22.json](evidence/gates/node22.json). Os logs integrais permanecem somente no diretório temporário da medição. Cada gate foi avaliado mesmo quando um anterior falhou. A suíte usou `npm test -- --maxWorkers=4` para limitar concorrência, com teto de 360 s por versão; mutações e prova receberam 180 s. Nenhum comando atingiu esses dois tetos.

## Causas e limites da atribuição

1. **Fim de linha de checkout — ambiente/harness Windows confirmado.** A configuração global do Git nesta máquina é `core.autocrlf=true`. `git ls-files --eol` mostrou `i/lf w/crlf` em `package.json`, YAML do CI e arquivos TypeScript; uma amostra tinha 792 de 792 quebras como CRLF. `prettier --check package.json` retornou 1 e o mesmo arquivo com `--end-of-line crlf --check` retornou 0, sem editar arquivos. Vários testes fazem regex `\n` ou mutações por âncoras textuais exatas e falharam sobre CRLF. Isso explica uma classe de falhas, **não** autoriza atribuir os 366 casos a essa causa. Escopo candidato: política explícita de EOL no checkout/formatter e contrato dos testes que leem texto bruto.
2. **Lançamento de subprocesso npm — incompatibilidade de harness reproduzida.** Com Node 20 e 22, `spawnSync('npm.cmd', ['--version'])` retornou `{status:null,error.code:'EINVAL'}` na sonda mínima. O catálogo de mutações chama `spawnSync('npm', ...)` e parou com `ENOENT`; testes de controle negativo também reportaram `spawnSync npm.cmd EINVAL`. Escopo candidato: um lançador de subprocessos portável e testado para a camada de scripts; a escolha de shell/argumentos deve ser revisada para não alterar o contrato de execução.
3. **Caminhos da prova — harness Windows reproduzido.** `path.relative('C:/tmp/repo', 'C:/tmp/repo/tests/workflow-shutdown.test.ts')` devolveu `tests\\workflow-shutdown.test.ts`, enquanto `prova/cancel-quiescente.ts` declara `tests/workflow-shutdown.test.ts`. O relatório JSON do Vitest contém ambos os arquivos e 48 assertions executadas; o resumo de `scripts/prova/vitest-relatorio.ts` usa `relative()` sem normalizar o separador antes de comparar. Escopo candidato: normalização explícita de caminhos internos da prova, preservando a checagem de zero testes.
4. **Filesystem/SQLite — divergência Windows observada, causa ainda aberta.** Há `ENOENT` em resolução de home `.lohra` e `EBUSY` em `rmSync` de `state.db` em testes que abrem conexões. A falha de limpeza pode ocultar a asserção primária; estas ocorrências exigem reproduções menores antes de atribuir defeito ao runtime ou ao teste. `tests/workflow-service-durability.test.ts:1458-1460` fecha uma conexão antes de `rmSync`, mas o log sozinho não prova qual handle ainda está aberto. Escopo candidato: inspeção de ciclo de vida de conexões/cleanup e do resolvedor de home sob caminhos Windows.
5. **Demais diferenças — não triadas individualmente.** Casos de permissão POSIX, processos/sinais, CLI/gateway e outros apareceram na lista de falhas. O total de 366 não foi repartido por causa, pois a contagem por família sem reprodução individual seria enganosa. Cada correção precisa de sonda mínima e issue deduplicada; nenhum teste foi enfraquecido para ficar verde.

Os recortes literais de saída e sondas mínimas estão em [samples.md](evidence/gates/samples.md). Os logs integrais das suítes têm hashes registrados nos JSONs para correlação, sem incluir dados de usuário.

## Controle Linux e conclusão da medição

O coordenador executou um **controle Linux real** em Docker `node:22-bookworm-slim`, mesma SHA obtida por Git bundle. Build, typecheck, lint e format passaram. A primeira suíte como `root` falhou em três testes de permissão porque esse usuário contorna `chmod`; a repetição como usuário não privilegiado `node` passou **318/318 arquivos e 4.216/4.216 testes**, exit 0. Esse controle separa divergências do checkout e plataforma Windows de um HEAD genericamente quebrado, mas não prova a causa de cada teste Windows. Metadados e hashes do controle estão em [linux-control.json](evidence/gates/linux-control.json). Mutações e prova Linux não foram medidas neste controle.

Esta investigação atende ao critério de registrar resultado independente para todos os gates, inclusive os bloqueios. Não declara suporte Windows. A próxima etapa útil é abrir correções pequenas por EOL, subprocesso e normalização de caminho, e sondar os erros de arquivo/SQLite em #703–#705 antes de decidir se são produto, harness ou ambiente.
