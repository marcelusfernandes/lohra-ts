# W8 — evidência nativa e plano de suporte Windows (#708)

Esta é a síntese do baseline `fa8aa4a572a8d84c3eea128a7ce67ab4eac796e1` (`0.0.13`) investigado em 2026-10-02. **Não declara suporte Windows.** W1–W7 mediram Windows 11 Pro x64 nativo, PowerShell 7.6.5 e, onde indicado, Node oficial portátil 20.20.2/npm 10.8.2 e 22.23.3/npm 10.9.9. O clone padrão falhou; os demais estudos usaram clones descartáveis com `git -c core.protectNTFS=false clone`, sem reparar silenciosamente a falha inicial. Cada relatório vinculado dá comandos, saídas sanitizadas e limites próprios. Nos [JSONs W2 Node 20](evidence/gates/node20.json) e [Node 22](evidence/gates/node22.json), apenas o prefixo pessoal dos campos `executionRoot` e `command` foi substituído por `<TEMP>` nesta síntese; exit, duração e hashes dos logs originais não mudaram. A proposta de implementação está em [backlog.md](evidence/consolidation/backlog.md).

**Fronteiras:** `PASS` de stub comprova encanamento local, não qualidade, disponibilidade, custo ou cache de um modelo real. #654 já trata medição live Anthropic de cache sob gate próprio; ela não satisfaz por si só uma futura amostra Windows. `untrusted` da tool de arquivo é metadado, não isolamento; tools executam no host com privilégios do processo. Shutdown de W4 fechou porta/processo mas não demonstrou limpeza graciosa. W2 não fez triagem individual de 366 falhas; nenhuma linha desta matriz deve ser multiplicada em 366 bugs.

## Interpretação e sequência

As causas Windows demonstradas que bloqueiam avançar são: checkout `aux.ts`, conversão EOL do checkout para CRLF, spawn de `npm` nos harnesses, normalização de caminho da prova, wrapper do terminal e comparação de raiz no workflow. `pack:check` traz incompatibilidade Windows estática adicional do nome do prebuild. `EBUSY` de `state.db` (incluindo W5), `ENOENT` de `.lohra` e os testes de serve/compactação requerem experimentos isolados antes de atribuir causa. Os demais casos da suíte Windows exigem nova triagem **após** corrigir os bloqueios de checkout/EOL/harness, agrupada por falha primária, sem atribuir causa aos 366 por contagem. A ausência de `dist/index.js`/`.d.ts` é defeito genérico do contrato de biblioteca; cron duplicado, lock órfão e perda de causa também são gerais pelo controle Linux. O [backlog](evidence/consolidation/backlog.md) mantém essas filas separadas e ordenadas por desbloqueio.

## Proposta de CI e critério de saída

Propor um **milestone futuro “núcleo Windows x64”**, distinto da investigação #700, de bugs genéricos e da TUI #619. Primeiro resolver checkout padrão e EOL; até lá, um job Windows informativo pode reportar sua própria falha sem mudar proteção de branch. Depois, acrescentar matriz `windows-latest` Node 20/22 com `npm ci`, `npm test`, `npm run build`, `npm run typecheck`, `npm run lint` e `npm run format:check`, na ordem do [CI atual](../../../.github/workflows/ci.yml), que roda testes antes de build para provar independência de `dist/`. A ordem canônica de gates locais do `AGENTS.md` é build → typecheck → lint → format:check → test; ambos cobrem os mesmos comandos. Acrescentar smokes locais de CLI/PTY/SQLite/gateway/serve e consumidor do tarball, sempre com homes temporários e stub; prova, mutações e `pack:check` entram depois de corrigidos seus launchers. Manter o job informativo até os testes e smokes repetirem verdes sem contorno de checkout; só então propor requisito de check em alteração **separada** de ruleset.

O custo de runner é **qualitativamente** uma matriz adicional de dois jobs Windows com addons e instalação npm. W2 mediu por Node cerca de 4 minutos somados para build/typecheck/lint/format/test (teste sozinho 116–121 s), **sem** checkout/npm ci nem overhead de CI; isto não é preço nem previsão de duração no GitHub Actions. Smokes e packcheck acrescentam tempo ainda não medido. Limitar concorrência do Vitest a 4 workers na fase de diagnóstico, como W2, e medir tempo em runners antes de tornar obrigatório.

Critério de saída do milestone proposto: checkout padrão Windows sem `protectNTFS=false`; `npm ci`/addons e gates canônicos verdes em Node 20/22 nativos por execuções repetidas; prova e mutações com resultado real; `terminalTool` e sandbox com testes de processo, caminho, symlink e cancelamento; chat/gateway/serve com stub, estado cross-process e encerramento gracioso demonstrados; tarball/`pack:check` e API de biblioteca compatíveis com contrato publicado; falhas gerais de cron tratadas no backlog próprio ou explicitamente excluídas com decisão de produto; documentação de plataformas e limites atualizada. Um smoke live só entra mediante autorização de credencial/orçamento e não substitui os testes locais; sem ele, a declaração de suporte deverá explicitar que a integração com provedores remotos não foi medida no Windows. Até cumprir esses critérios e medir o CI, Windows permanece não suportado no produto.
